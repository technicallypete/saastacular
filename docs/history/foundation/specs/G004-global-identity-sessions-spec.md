# G004 — Global identity and sessions work specification

Goal: [G004-global-identity-sessions.md](../goals/G004-global-identity-sessions.md)

## Goal, Rationale and Authority

Establish one global user identity backed by an external provider and a core-authoritative application session. Prove sign-in, current-account resolution, logout/revocation, failure behavior and MFA/SSO capability without introducing tenant authority or a custom authentication provider.

Follow AGENTS.md, CLAUDE.md, BUDGET_POLICY, ARCHITECTURE §§3/35/37/47/53.2/54/56/57/60, accepted ADRs and the roadmap. Architecture and product-owner decisions govern; this Spec defines outcomes and security constraints. Claude owns the concrete provider adapter, module layout, route names, migration design and Plan. No product-specific work is allowed before G021 acceptance.

## Requirements

### R1 — Provider Boundary and Trust Configuration

Use **WorkOS AuthKit** through a core-owned `IdentityProvider` interface, per accepted ADR-003. Authentication cryptography/protocol processing uses maintained, reviewed libraries; no handwritten token verifier or identity server. The historical OIDC configuration placeholder does not define the AuthKit API. Provider SDK types do not become domain identity or permission types; do not move authority into a Next.js auth SDK or install a second provider.

The Plan pins compatible SDK/library/test-tool versions, WorkOS environment/client binding, exact issuer and trust endpoints, algorithms, capabilities, callback/return origins and test environment. Hosted service releases are not represented as a fictitious pinnable server image. Discovery where used, API exchange and key retrieval accept only configured provider trust endpoints; token-supplied URLs, arbitrary issuers and request Host/forwarding headers cannot choose an endpoint. Bound network waits/body sizes and key-refresh concurrency; unknown keys fail validation until a trusted refresh succeeds. Do not follow arbitrary redirects or fetch attacker-selected metadata. Pin the issuer's exact spelling/namespace and stable subject behavior across callbacks; any future auth-domain/environment migration requires explicit mapping review, never automatic email linking.

Misconfiguration fails closed and reports variable names/codes without values. Existing anonymous health routes keep accepted semantics. An explicitly unconfigured local foundation may keep health/shell available but cannot authenticate anyone; production configuration cannot silently enable a development bypass or accept incomplete enabled auth. Provider credentials are server-only and never sent to intelligence or browser bundles.

### R2 — Global Identity and Minimal Persistence

Assign each application user an immutable canonical UUID. Bind an authenticated provider principal by the exact validated issuer and subject, with a database-enforced unique mapping. Names, email, hostname, provider labels and external subject values are alternate attributes/references, not the application primary identity. Email/name changes preserve the UUID; equal emails must never auto-link different principals. No user-supplied UUID or claim can select somebody else's existing account.

Repeated and concurrent first sign-ins for one principal create exactly one user mapping. Mapping creation and session issuance are transactional: failure cannot publish a usable session referencing an absent/incorrect user. Reject empty/bounded-invalid identifiers and duplicates according to the reviewed contract. A disabled local user remains disabled across sign-in, issuer outages and restarts; successful upstream authentication cannot reactivate it.

Persist only identity/session data needed here; no Organization/Group/BusinessEntity/membership/RoleBinding table, foreign key or role field. Global users/bindings are not tenant-owned rows. Infrastructure/framework tables, including session/transaction registries, may use another key strategy if the Plan justifies it; bearer credentials are not canonical domain IDs. Durable identity and revocation facts use PostgreSQL; Redis may hold ephemeral transaction/cache state but cannot restore authority lost from durable state.

### R3 — Provider Sign-in and Callback Validation

Use WorkOS's documented provider-redirect Authorization Code exchange with mandatory PKCE S256 and core-side exchange. The application must not receive the user's password or own factor enrollment. Bind each login transaction to its initiating browser, configured client and callback using one-use state and verifier; generate state unpredictably with at least 128 bits of randomness. An OIDC ID-token flow, if actually used, additionally requires a transaction-bound unpredictable nonce; do not invent a nonce field in a protocol that does not return one. Callbacks with absent/expired/mismatched/replayed transactions cannot create or replace a session. Login transactions expire no later than ten minutes after initiation. Do not use implicit flow or a production password grant. ([OAuth security BCP](https://datatracker.ietf.org/doc/html/rfc9700), [PKCE](https://datatracker.ietf.org/doc/html/rfc7636), [WorkOS code exchange](https://workos.com/docs/reference/authkit/authentication))

Only an authenticated response from the configured WorkOS exchange, bound to the pending code/client/verifier, can supply the provider user. Before mapping, validate the accompanying signed token's signature/algorithm, exact issuer, exact configured `client_id` and any applicable audience, subject, expiry and required time claims; its subject must equal the returned WorkOS user ID. Reject unsigned/tampered/wrong-client/wrong-kind/inconsistent tokens and arbitrary browser-supplied provider assertions. WorkOS AuthKit access tokens are not generic OIDC ID tokens: the Plan specifies the documented token contract and rejects confusion between token types; OIDC nonce/authorized-party rules apply only to an actual ID-token flow. Pin clock leeway at no more than 60 seconds. Trusted signing-key rotation must work; an attacker-selected key/algorithm must not. Any unavailable required client, identity or assurance proof is escalated before implementation, not replaced by a weaker fallback. ([WorkOS token contract](https://workos.com/docs/reference/authkit/session-tokens), [JWT BCP](https://datatracker.ietf.org/doc/html/rfc8725))

Honor only configured callback URLs and validated local return paths. External, scheme-relative, encoded/traversal or forged-host redirects cannot escape the allow-list. Login cancellation/provider errors produce bounded safe responses and no authenticated session. A failed or unsolicited login must not switch an already authenticated browser to another user. Concurrent transactions remain isolated; no unauthenticated GET silently replaces an existing identity. All server-side auth network operations have a finite application deadline of at most ten seconds, excluding interactive provider pages; the Plan specifies testable response codes and per-call bounds.

### R4 — Core-Authoritative Application Sessions

Browser authentication resolves through core, not claims asserted by web, cookies containing unverified user data, email or headers. Use an opaque browser session credential, generated with at least 256 bits of cryptographic randomness, with server-side user/status/expiry resolution. Do not store bearer session or provider tokens in localStorage/sessionStorage, URLs or browser-readable application state. Durable session lookup stores a one-way representation of that credential, not the usable bearer value. Any retained provider credential requires justified server-side encryption/key separation and exact grants; avoid requesting offline access/refresh credentials when unnecessary.

The Plan defines positive finite idle and absolute lifetimes, with absolute expiry never extended by activity or renewal. Recommended starting values are 30-minute idle and 8-hour absolute expiry, to be pinned at Plan review. Expired, revoked, disabled-user, forged, unknown and duplicate/ambiguous credentials cannot authenticate. Successful sign-in replaces/rotates the pre-auth credential; rejected credentials cannot be promoted. Any renewal produces no resurrection of expired/revoked authority.

Each authenticated request checks current session/user authority. Logout/revocation acknowledged as committed must deny the old credential on the next request begun afterward, across every serving replica; an outage, stale cache, restart or concurrent refresh cannot resurrect it. Requests already in flight are documented separately. Core restart may retain a still-valid durable session or intentionally invalidate it, as pinned in the Plan; identity stability and revocation survival are mandatory either way. Loss of ephemeral Redis state may invalidate pending login but cannot grant authentication. Unavailable authoritative session/user state returns a bounded service failure, never an authenticated cached success.

### R5 — Browser Origin, Cookie and Mutation Protection

Use host-only session cookies: no `Domain` spanning sibling tenant hosts. In the production/test HTTPS profile require `Secure`, `HttpOnly`, `Path=/`, an explicit reviewed SameSite policy and the corresponding hardened cookie-name rules. Pin attribute/expiry/deletion behavior and test it in a real browser. A separately flagged loopback-only HTTP development profile may relax only Secure/name rules; production refuses it. Merely testing HTTP `.localhost` does not establish TLS/callback behavior. ([Session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), ARCHITECTURE §60)

Authentication-affecting mutations are unsafe methods with server-validated CSRF protection and trusted origin checks; valid cookies alone cannot authorize cross-site logout/all-session revocation. No GET performs account/session revocation. Login-CSRF protection is the browser-bound R3 transaction, distinct from mutation CSRF. Reject missing/mismatched CSRF and unsupported origins/content types without state changes. No wildcard credentialed CORS, trusted user/context header from the browser or unvalidated forwarding-header trust. ([CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html))

Authenticated account responses use `no-store` and are not shared by CDN/Next/BFF caches. Concurrent users, browser contexts and requests cannot see one another's account data. A caller receives only its own minimum account/status data; no arbitrary-user lookup/list/update surface.

### R6 — Logout, Revocation and Account Disable

Current-session logout commits local revocation before reporting success, clears its cookie and is safe to repeat. A copied old credential is denied even if the provider session remains active. Self-service logout-all revokes every existing application session for the caller while preserving other users' sessions. New sign-in afterward is a new session, not revival of a revoked one. Logout failure to commit revocation is not reported as successful durable logout.

Provide a trusted core operation to disable/re-enable a global user, tested internally without inventing a public administrator or accepting a browser-supplied admin role. Disable revokes that user's existing sessions and blocks new ones until an explicit trusted re-enable; re-enable cannot revive old sessions. No automatic provider-claim-based role or administrative grant.

Separate local logout from provider SSO logout. Integrate WorkOS's documented logout capability with allow-listed registered return destinations; upstream timeout/error cannot undo already committed local revocation. Pin necessary non-bearer provider session references, return correlation and the distinction between initiated/unconfirmed and verified provider completion. Document whether it ends other relying-party sessions and never promise global logout without evidence. Do not force unsupported OIDC logout parameters onto AuthKit. ([WorkOS logout](https://workos.com/docs/reference/authkit/logout)) Automatic remote disable/back-channel synchronization is required only if the selected ADR claims it; otherwise document its absence and the explicit local disable path. Do not claim external deprovisioning is instantaneous.

### R7 — Provider MFA/SSO Capability and Honest Session Assurance

Per the owner-approved ADR-003 clarification, enable provider-owned MFA for the real qualification environment and demonstrate its capability. Keep application session MFA assurance **unknown** unless an explicitly reviewed trusted proof establishes MFA for that particular session. A provider environment setting, authentication method, requested challenge, periodic test, browser parameter or unvalidated claim cannot mark it achieved. Do not persist, return or use `mfa_by_provider_policy` or an equivalent policy-derived assurance label. Provider configuration/evidence is recorded separately from session assurance; no domain role or Organization policy is inferred from it.

Ordinary sign-in may create an otherwise valid session with unknown MFA assurance; missing MFA metadata alone does not deny that sign-in. All identity/client/signature/time, callback, PKCE, session and revocation requirements remain mandatory. Any request or test profile specifically requiring **verified MFA** fails closed when session-specific proof is missing, insufficient, forged or unreviewed. Define this denial in the owned authentication boundary and tests; no new public step-up route, product operation or local factor UI is authorized. A future proof source/mapping requires explicit security/Plan review before acceptance, not an inferred fallback.

Demonstrate one real provider-owned MFA challenge success and cancellation with synthetic accounts; cancellation or an incomplete challenge issues no application session from that transaction. Demonstrate one real SSO reuse flow: discard/revoke the local session, sign in again using the retained provider SSO session, and resolve the same global UUID without application-owned credentials. Sessions from both successful flows remain unknown for MFA without the separately reviewed proof. Demonstrate forced reauthentication when configured freshness is unmet, independently validating signed `auth_time`; missing/forged/stale required authentication-time metadata remains a failure.

Deterministic tests prove that valid ordinary sign-in without MFA metadata yields unknown assurance; provider-policy/authentication-method assertions and forged MFA labels cannot upgrade it; unknown/unsupported assurance denies a verified-MFA requirement; invalid identity/freshness still fails; and canceled transactions issue no session. Include a policy-drift case showing that disabling required MFA cannot cause a false verified-session claim. These tests complement, not replace, required real-provider MFA/SSO/freshness evidence.

Enterprise SAML directories and per-Organization connection administration remain outside G004. The ADR/docs must identify the chosen provider's SSO/federation capability and required future configuration; no unsupported enterprise-completion claim.

### R8 — Minimal Browser/BFF Surface and Service Boundaries

Offer configured-identity sign-in, current-user display and current/all-session sign-out, plus accessible loading/canceled/failure/signed-out states. Exact paths/methods/statuses/fields belong in the reviewed Plan. Anonymous account requests are 401 with no user data; invalid/expired/revoked sessions are denied, CSRF violations are 403, and unavailable authoritative state is 503 without identity disclosure. The Plan pins remaining callback/provider error codes.

Treat provider-derived display values as untrusted text: no HTML/script interpretation or unsafe redirect interpolation. Reject duplicate/ambiguous callback parameters and authentication credentials rather than selecting an attacker-controlled occurrence. Tests include a hostile display value and ambiguous callback input.

Web forwards only the allowed authentication/session inputs to core through server-only wiring; core validates them itself and performs provider exchange/mapping/session authority. Browser calls stay on the web origin or the intended provider redirect, never direct core/intelligence/datastore fetches. No provider token is an intelligence credential. User authentication does not change intelligence's internal service authentication. Core's directly reachable auth/account HTTP paths enforce the same rules and cannot trust a BFF-supplied user UUID or role header.

Retain the actual accepted post-G048 semantic styling/Radix components/fonts, keyboard/focus/landmarks, Light/Dark/System, first paint/hydration and scoped tokens, per ADR-001. Use existing primitives where sufficient; no visual redesign or component-library rollout. Provider-hosted pages are external surfaces whose tested capabilities and accessibility limits are disclosed; application checks still gate owned routes.

### R9 — Migrations, Privacy and Failure Controls

Use the accepted migrator/NOLOGIN-owner path for identity/session schema. Runtime has only necessary table/sequence grants, no ownership, DDL, privileged role assumption or access to migration metadata; web/intelligence receive no database/provider-client secrets. New objects preserve owner/default-privilege rules and runtime CRUD must work on actual PostgreSQL. Unique constraints/foreign keys enforce R2 even under concurrent login. Apply/up/restart/rollback/reapply tests on disposable databases; record destructive rollback implications. Do not edit the accepted baseline migration or run down/reset against developer data.

Reuse accepted G003 structured correlation/redaction. Record bounded login/session outcomes without authorization codes, state/nonce/verifier values, cookie/CSRF/bearer/provider tokens, raw claims, emails, passwords or factor secrets. Return errors without upstream bodies/stack traces. Seed synthetic canaries into success/error/callback/provider paths and prove the scanner detects a planted leak; suppressing all auth diagnostics is not a privacy test. Evidence/source/build contexts must contain no real provider credentials or test factor secret.

Retain deterministic invalid-token/transaction, forged-header, cross-user, CSRF, revoked-cookie, parallel-session and outage controls. Test helpers/mock issuers are isolated to test artifacts. Any runtime development authenticator must be expressly reviewed, opt-in, and refused in production; no reusable fake-login bypass is required or authorized by this Spec.

### R10 — Containerized Integration, Provenance and CI

Name exactly which commands/configuration require provider access and which deterministic checks run offline. Plan pinned official WorkOS-emulator fixtures for deterministic failure/browser integration checks and an approved restricted real WorkOS staging environment for service qualification. Emulator success is not real authentication, MFA or SSO evidence; isolate it to test artifacts and make production reject emulator/test endpoints. No additional identity vendor is introduced for tests. Retain attributable real-browser code/callback, MFA, SSO-reuse and reauthentication qualification before acceptance, using a bounded human-driven procedure when necessary; record exact tree/configuration, safe observations and outcomes. Separately run real staging API/adapter integration checks in approved protected hosted CI. Describe which credentials/setup those checks need and the supported emulator feature matrix. No bypass login endpoint or session injection can stand in for required sign-in/callback evidence. This separates the evidence layers without deferring required evidence outside G004.

Required real-provider integration evidence is attributable to the submitted tree. CI may run it against a disposable approved provider or an approved restricted test tenant; credentials never become artifacts or available to untrusted MR code. If an unsafe secret exposure would be required, redesign the reviewed test arrangement or escalate; do not mark required evidence optional. At least one hosted run on the final implementation must include the integrated required checks. Authorization for that run is separate from this draft.

Preserve both Skills, source kits, original `.archetype` manifest, architecture/governance and closed-goal artifacts.
