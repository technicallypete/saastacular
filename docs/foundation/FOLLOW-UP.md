# Foundation follow-up

The archetype rendered a minimal, verified skeleton. The obligations below are **prescribed, not yet implemented**: each foundation stage must implement them and prove them with the stated verification. None of them is passed by the skeleton alone. Treat this list as the backlog of foundation work before any product feature is built.

Stages are generic; map them to your own planning identifiers.

## STAGE-BOOTSTRAP — repository and local platform
- [x] Adopt the rendered layout; keep root names describing responsibility (`web`, `core`, `intelligence`, `contracts`, `infra`). *Done in this repository's bootstrap; see [BOOTSTRAP.md](BOOTSTRAP.md).*
- [x] Choose and pin a migration tool (for example goose, golang-migrate or Atlas); run migrations as the migrator role through `SET ROLE <db>_owner`, in a container. *Done: goose, embedded in the `migrate` image; see [MIGRATIONS.md](MIGRATIONS.md).*
- [ ] Add the MCP server initialization in `core` (official MCP Go SDK) only together with authentication from STAGE-IDENTITY; never expose an unauthenticated MCP endpoint. *Done (MCP connections, migration 00010): mounted only when MCP is configured, behind the trusted host registry and Connect token verification; the setup page needs a signed-in member ([MCP.md](MCP.md)).*
- Verify: clean container-only start; migration up/down in a disposable database; rename via `.env` only.

## STAGE-IDENTITY — global identity and sessions

- [x] Any development-only identity adapter must be behind a build tag or explicit flag and must refuse to start when `APP_ENV=production`. *Done: there is no development adapter. ## STAGE-TENANCY — Organization, Group, BusinessEntity
- [ ] `organization_id` on every tenant-owned row; `TenantContext` is a security envelope, never a persisted tenant table. *Partly done: Organizations, Groups and role bindings carry `organization_id`; no persisted tenant table. TenantContext is an in-process, request-scoped envelope, never persisted; see [TENANCY.md](TENANCY.md) and [AUTHORIZATION.md](AUTHORIZATION.md).*
- [ ] Group: immutable UUID, editable kebab-case slug, `UNIQUE (organization_id, slug)`, reserved-route validation; slugs never grant access. *Partly done: the model, its constraints, the 24-entry reserved set and suggestion rules exist as internal primitives. Group onboarding adds Group creation with a suggested, editable slug through the guarded facade and the web onboarding pages; Group rename and slug change stay Go-only guarded operations with no route, so slug administration UX remains.*
- [x] BusinessEntity shared by many Groups through GroupBusinessEntity, with same-Organization enforcement by composite foreign keys **and** service validation. *Done, under the foundation's names and cardinality: an Organization-owned `BusinessProfile` shared by several Groups through `GroupBusinessProfile`, at most one per Group, with composite same-Organization foreign keys and Organization-scoped service prechecks; no BusinessProfile role or grant, and access facts derived from Group bindings. See [TENANCY.md](TENANCY.md).*
- [ ] Memberships keep their canonical shape (user, scope, role); confirm how membership roles derive from RoleBinding so there is a single mutable authority store. *Partly done: `role_bindings` is the only role store; Organization and Group memberships are its read-only projections, and a Group's creator starts as `group_owner`. There is no BusinessProfile membership. Policy evaluation over the bindings is described in [AUTHORIZATION.md](AUTHORIZATION.md); membership administration in [TENANCY.md](TENANCY.md#membership-ownership-and-invitations).*
- [ ] Preserve BusinessEntity → many BillingProfiles without implementing billing. *Partly done: `business_profiles_organization_id_key (organization_id, id)` is the composite target for future BillingProfile children, with no singleton on the profile; billing itself remains.*
- Verify: cross-Organization association rejected by the service and by the database; slug collision and reserved-name tests. *B-BUSINESS-PROFILE-IT rejects cross-Organization associations in the service and in a 27-combination runtime SQL matrix; the tenancy tests cover slugs.*

## STAGE-POLICY — shared RoleBinding policy
- [x] One policy system over `RoleBinding(subject, scope_type, scope_id, role, source)`; deny by default. *Done: one closed, deny-by-default evaluator over the current membership bindings, eleven capabilities and six roles, with no ranking, prefix matching or global authority (`core/internal/tenancy/access`); it is internal, and no public adapter exists yet. See [AUTHORIZATION.md](AUTHORIZATION.md).*
- [x] Capability-specific inheritance from Groups to BusinessEntities computed at evaluation time; no mirrored permission rows. *Done, under the foundation's names: BusinessProfile paths are computed per operation from current Group bindings and the Group's single association (`linked`, and `linked+flag` under the Organization's one policy flag); no permission row, grant or cache exists.*
- [ ] Sensitive operations (ownership, privileged settings, policy, audit, role grants) require direct BusinessEntity or Organization authority. *Partly done: there is no BusinessProfile authority; privileged settings, Organization policy and audit are `org_owner`-only with no Group path, and the policy update is a guarded operation.* *Membership administration (migration 00015): guarded promotion, demotion, transfer, role change, removal and departure with the version-15 authority guard ([TENANCY.md](TENANCY.md#membership-ownership-and-invitations)).*
- [x] Context resolved on the server from the authenticated session; client and model identifiers are selectors only. *Done as the internal resolver: one request scope per authenticated session request, Organization and Group UUIDs as selectors, current membership required, no default Organization; correlation IDs, headers, claims and model data are never inputs. Transport adapters (HTTP, MCP context switching, hostnames) remain with their stages.*
- Verify: permission-matrix tests; forged identifiers behave like nonexistent ones; role removal changes access with one row change. *U-POL-MATRIX (an independently written matrix) and the matrix on database-loaded facts (B-POLICY-IT); unknown, foreign and inaccessible targets share `not_found` or `context_denied`; removing one binding row changes the next decision, also inside an unchanged request scope; B-POLICY-ORDERING covers in-flight writes.*

## STAGE-RLS — PostgreSQL row-level security and roles
- [x] ENABLE and FORCE row-level security on every tenant table; per-command policies; same-tenant composite foreign keys. *Done: five tenant tables, `users` and three authentication tables, 26 policies (`00006_row_level_security.sql`, [DATABASE-ISOLATION.md](DATABASE-ISOLATION.md)).*
- [x] Transaction-local context (`set_config(..., true)`) in every request transaction; missing or malformed context fails closed. *Done: one guarded statement first in every facade and identity transaction; prior context discards the connection.*
- [x] Runtime role: never superuser, never BYPASSRLS, never owner or member of the owner; SECURITY DEFINER functions narrowly scoped, `search_path` pinned, allowlisted. *Done: five readers owned by two NOLOGIN helpers.*
- [x] Production role provisioning: managed PostgreSQL does not run init scripts; create the same role separation through provisioning. *Done: `infra/postgres/provision-roles.sql`.*
- Verify: runtime-role attack suite (cross-Organization reads and writes, absent and malformed context, pooled connection reuse), privileged-connection guards, owner FORCE tests. *Integrated attack chains across context, facade, runtime SQL and provider (`TestIsolationAttacks` in B-OBJ-IT, [AUTHORIZATION.md](AUTHORIZATION.md#isolation-attack-suite)); the single-boundary cases stay with the row-level-security and object-storage suites.*

## STAGE-STORAGE — object storage

- [x] Scoped, server-resolved credentials (never root credentials in the application).
- [ ] Re-evaluate the local object store before any non-local use (see [VENDORS.md](VENDORS.md)); R2 configuration notes are in [OBJECT-STORAGE.md](OBJECT-STORAGE.md), without live-cloud qualification.
- Verify: foreign-object and prefix-guess denials; expired and sibling-key URLs fail; anonymous bucket access denied (B-OBJ-IT, B-OBJ-ORDERING, B-OBJ-FAULTS).
- Related: the isolation attack suite reuses the storage world, oracle and attack surfaces; the audit records storage outcomes and issuance durably ([AUDIT.md](AUDIT.md)); recovery and retention deliver tombstone purge after absence and ledger preservation, the pending/deleting repair through the guarded delete, and the audit maintenance contract ([RECOVERY.md](RECOVERY.md)).

- [ ] Encryption in transit and at rest for production; backup and restore procedures with periodic restore tests; retention and deletion hooks; incident runbooks; vendor inventory upkeep. *Partly done: the transport and at-rest matrix and the configuration-only readiness evaluator (`core/cmd/readiness`; the current production result is blocked), and the vendor data-handling records in [VENDORS.md](VENDORS.md). - [x] Control-plane tools: `account.get_current_user`, `account.get_current_context`, `context.list_groups`, `context.switch_group`, `logout`; no Organization-switching tool. *Done.*
- [x] Group selection/clear validates current authority within the bound Organization and recalculates this connection's catalog; failures retain previous context, and other connections/browser context remain independent. Ordinary tool arguments never switch tenants. *Done: the catalog is the fixed five tools; selection is stored per connection.*
- [ ] `tools/list` shows only capabilities available in the active context; every execution reauthorizes identity, context, membership, resource ownership, capability and approval; stale catalogs fail at execution.

Also prove separate tenant/same-tenant connection isolation and endpoint/session replay rejection. Follow [the MCP connection contract](../../contracts/mcp/connection-context.md); historical archetype switching fixtures are not new-contract evidence.

- [x] Create Group, then create or select an existing BusinessEntity under sufficient owner or admin authority, then create the association, then complete onboarding. *Done, under the foundation's names: any current Organization member creates a Group and becomes its `group_owner`; completion attaches a new or an existing eligible BusinessProfile, and a Group is complete exactly when its single association exists ([TENANCY.md](TENANCY.md#group-onboarding)).*

- Verify: unauthorized selection fails; completion is impossible without the association; invitation replay fails. *ONB-1..13, O-ONB-1..3/D/E, the oracle insert rows, attack steps B2/C3 and E-ONB-1..7.*

Recorded residual, not addressed: `pg_resetwal` moving a cluster's transaction counter backwards is an OS-level destructive operation outside the supported recovery path and the profile insertion-provenance model ([RECOVERY.md](RECOVERY.md)).

## STAGE-AI — internal intelligence (only when enabled)
- [ ] Core owns the public streaming lifecycle (SSE, WebSocket or streaming HTTP), cancellation and deadlines, tool approvals and commit gates; it translates intelligence events and never exposes them directly to the browser.
- [ ] Core-signed, short-lived, audience-bound execution envelopes (the skeleton's static service token is a starting point only).
- [ ] Authorized callbacks: a callback presents its grant reference; core reauthorizes against current grants and ignores tenant identifiers supplied by intelligence.
- [ ] Retrieval filtered before the model; scoped memory; durable usage records built by core from its own envelope (user, Organization, Group, BusinessEntity) joined to usage events; observability vendors are never the ledger and receive no content by default.
- [ ] Decide whether embeddings need a direct-provider adapter behind `ModelGateway`.
- Verify: revoked grant denies callbacks; forged attribution in events rejected; retrieval leakage tests; trace privacy tests.
