# Object storage

Tenant-aware object storage behind core's owned boundary. Metadata rows in PostgreSQL (migration
`core/migrations/00007_stored_objects.sql`, version 7) anchor every decision; the provider holds only bytes under
server-derived keys. The increment is route-less and core-internal: nothing wires it into a binary yet. A later
reviewed adapter builds `access.NewServiceWithObjects` from `config.Load`'s settings and owns transport concerns
(request deadlines, concurrency, admission and rate limits).

## Components

| Part | Where | What it does |
|---|---|---|
| Provider boundary | `core/internal/objectstore` | `Store`: Put, Get, Delete, SignedGetURL and Metadata (Head) of one validated key `objects/<organization uuid>/<object uuid>`; closed errors (`ErrNotFound`, `ErrDenied`, `ErrUnavailable`, `ErrOutcomeUnknown`, `ErrInvalid`) without provider text. The S3-compatible adapter uses the pinned aws-sdk-go-v2: one data client and one presign client, a bounded transport (dial 5 s, TLS 5 s, response header 15 s, idle 90 s, 16 idle connections per host) and no automatic retries. Only `core/internal/tenancy/access` imports it. |
| Metadata | `app.stored_objects` | UUID identity (generated by core before the insert), required Organization, optional Group of that Organization (composite foreign key), immutable creator, the database-generated key, size, content type, SHA-256 (from ready on), and the lifecycle. Tombstones keep their attribution; runtime never deletes rows. |
| Guarded operations | `core/internal/tenancy/access` | `PutObject`, `ObjectMetadata`, `GetObject`, `SignedGetURL`, `DeleteObject` ([AUTHORIZATION.md](AUTHORIZATION.md)). |
| Record | `storage.operation` | One per call: operation, outcome, closed reason, Put/Delete stage, UUID attribution (actor, Organization, optional Group, object once known), issued TTL, physical delete outcome, request/trace correlation. Never a URL, signature, credential, key, payload, content type, size, filename or provider text. Operational evidence, not the durable audit ([AUDIT.md](AUDIT.md)). |

## Authorization

| Action | Organization object | Group object (owning Group g; explicit Group authority, migration 00017) |
|---|---|---|
| read (Metadata, Get, Sign) | organization.read | any current explicit role in g |
| put | org_owner, org_admin | any current explicit role in g |
| delete | org_owner, org_admin | group_owner/group_admin of g; group_member of g only as the stored creator |

Explicit Group authority ([AUTHORIZATION.md](AUTHORIZATION.md#explicit-group-authority-supersedes-the-all-management-cells-above))
removed the Organization owner/admin shortcuts to Group objects (previously `group.read` on g for reads, and
`org_owner`/`org_admin` for put and delete) in core and in the `stored_objects_*` policies, under either setting of the
Group-management override: reading a Group's metadata, selecting it or administering it through the override confers no
object access.

Each operation runs the binding check, then, in one short storage transaction: the context statement, the live
session, row-level-security discovery of the object's immutable scope, the bounded facts of that scope (the owning
Group plus the selected Group; never every binding), the context check and the decision. All of it happens before any
provider call or disclosure. Missing, foreign, inaccessible, outside-context and non-ready objects are `not_found`; a
readable object whose action is denied is `forbidden`. Row-level security enforces the same table independently
([DATABASE-ISOLATION.md](DATABASE-ISOLATION.md)): read scope for SELECT, upload scope with the subject as creator for
INSERT, lifecycle scope for UPDATE, no DELETE grant at all.

## Lifecycle

```
            T1 insert              T2 publish (creator only)
   (none) ───────────────▶ pending ─────────────────────────▶ ready
                              │                                 │
                              └──────────── D1 ───────▶ deleting ◀┘
                                                          │
                                                 D4 (absence confirmed)
                                                          ▼
                                                       deleted (tombstone)
```

The guard trigger refuses every other transition, same-state updates, any update of a deleted row, and changes to the
identity columns. Pending and deleting objects never serve new reads or signed URLs.

**Put.** P0 owns the Body and validates (size required, at most the configured maximum; content type; body present).
P1 probes a zero-length upload for extra data. T1 authorizes and inserts the pending row (`INSERT … RETURNING`; the
database-generated key is compared with the key core derives before any upload). P2 streams exactly Size bytes to the
exact key outside any transaction, through an exact reader that releases the final byte only after the source reports
EOF, under the transfer deadline (cancellation or the deadline closes the source; an in-flight Read is reaped for at
most 5 s). V checks the stored length and binding metadata with a Head. T2 re-authorizes and publishes the row as ready
with the local digest. An unknown T2 COMMIT is reconciled by locking the row (R): ready means success; anything else
is compensated.

**Invariant I-FIN.** Only the call that inserted a pending row can finalize it, inside that call; there is no resume
API. Compensation (C: provider delete, confirmed absent by a Head) runs only when the row is authoritatively not
ready: a definitive T2 outcome or R's locked read. It never runs after an unknown COMMIT without R, so possibly
committed bytes are never destroyed. Compensation runs detached from the caller's cancellation, bounded by 10 s per
provider call.

**Delete.** D1 decides on the object's immutable scope and creator and marks it deleting (an authorized repeat delete
of a deleting or deleted row re-runs the removal); D2/D3 remove the bytes and confirm their absence; D4 re-authorizes
and tombstones the row. The result is `deleted` only when the row is a tombstone and absence is confirmed, otherwise
`deletion_pending`. A failed provider delete is never reported as confirmed.

## Integrity: what is and is not proven

- The stored `sha256` is the digest of the bytes core delivered to the transport.
- V proves only the stored length and the binding metadata. Neither independently proves that the stored payload
  equals those bytes: uploads use `UNSIGNED-PAYLOAD` (streaming, no buffering) and send no provider checksum.
- `GetObject` verifies the stored content against `sha256` while streaming; a mismatch is an `internal` error at EOF,
  after any delivered bytes. The returned reader is bounded to the stored size, and Close cancels the transfer.
- **Signed downloads are served by the provider directly and are not verified by core (residual X7).**
- Production transit integrity relies on TLS: with `APP_ENV=production` both the data and the signing endpoint must be
  https.

## Settings

All optional and defaulted; read and validated by `config.Load` at startup (problems name only the variable) and
re-enforced by `objectstore.New` and `access.NewServiceWithObjects`.

| Variable | Default | Bounds |
|---|---|---|
| `OBJECT_STORE_SIGNING_ENDPOINT` | `OBJECT_STORE_ENDPOINT` | an absolute http(s) URL with a host and an optional port, nothing else |
| `OBJECT_STORE_MAX_OBJECT_BYTES` | 26214400 (25 MiB) | 1..1073741824 (the hard cap, also enforced by the database) |
| `OBJECT_STORE_SIGNED_URL_DEFAULT_TTL` | 60 | 1..300 seconds, at most the maximum |
| `OBJECT_STORE_SIGNED_URL_MAX_TTL` | 300 | 1..300 seconds |
| `OBJECT_STORE_TRANSFER_TIMEOUT` | 120 | 1..900 seconds |

Endpoint transport rules: the data endpoint has the same absolute-URL shape; production refuses http for either
endpoint; an http data endpoint with an https signing endpoint is refused everywhere; http for both is allowed in
development and test (local MinIO). Fixed bounds: 5 s decision budget per storage transaction (BEGIN through COMMIT)
and 5 s cleanup budget for its deferred rollback, 10 s per provider control call (Head, Delete), 5 s source reap grace.
These are limits, not latency or concurrency guarantees.

## Signed URLs and endpoint identity

The presign client signs offline over the trusted signing endpoint: method GET only, the exact key from the row,
`X-Amz-Expires` = the TTL, and fixed response overrides `response-content-disposition=attachment`,
`response-content-type=<stored type>` and `response-cache-control=no-store`. No request header is read and the URL is
never rewritten. SigV4 binds the `Host`, including its port.

- **Local browser access:** set `OBJECT_STORE_SIGNING_ENDPOINT=http://127.0.0.1:<MINIO_API_PORT>` (BIND_ADDRESS plus the
  published API port). Docker port publishing forwards the browser's `Host` unchanged, so the signature verifies; the
  harness proves it by fetching the unchanged URL through the published port (OBJ-SIGN-HOST).
- **In-network consumers:** the default (`http://minio:9000`) is valid only on the data network.
- **Secrecy:** the URL and its query are a bearer secret. `SignedURL` redacts it in `String()`, `GoString()` and
  `LogValue()`; core never logs or stores it. Its path reveals the Organization and object UUIDs to its holder.
- **Revocation (residual X1):** an issued URL stays usable until it expires (at most 300 s) or the bytes are removed,
  even after revocation or logical deletion; in-flight transfers complete. New issuance and new guarded reads are denied
  at once.

## Failure, repair and retry

There is no daemon, queue or bucket scan. Every failure leaves an attributable row:

| Failure | State | Repair |
|---|---|---|
| Unknown T1 COMMIT (X2) | possibly an inert pending row without bytes | an authorized Delete |
| Compensation failure or a late in-flight PUT (X3) | inaccessible bytes under a non-ready row | an authorized Delete |
| Unknown T2 COMMIT with reconcile unavailable | the row may be ready; bytes kept | a retry of the read, or an authorized Delete |
| D1 unknown, D2/D3/D4 failure | deleting (`deletion_pending`) | a repeat Delete by an authorized deleter |
| A source that ignores Close (X6) | `unavailable` (`source_not_released`) within the grace; never published, compensated | the caller's source |

A retry is always a new, re-authorized operation; the SDK never retries. Residual X4: a holder of the runtime
credential with arbitrary SQL can finalize its own pending row without bytes (the existing trust limit); a later read
is `not_found`.

**Query-cost observation:** the Put T1 `INSERT … RETURNING` makes 4 `rls_org_role` and 2 `rls_group_role` calls (the
INSERT WITH CHECK plus the SELECT policy of the returned row) against an expected ≤2/≤1, identically at 1 and 50 Group
bindings. It is recorded as a characterized observation and remains an open performance question.

## Related stages

- **Isolation attack suite:** reuses the storage world, the oracle and the attack surfaces (selectors, keys, signed URLs, the provider boundary).
- **Audit:** durable audit ([AUDIT.md](AUDIT.md)). Row transitions are recorded by capture triggers in the same
  transaction (`object.upload_started`, `object.ready`, `object.delete_started`, `object.deleted`); a signed URL is
  returned only after its `object.url_issued` event (TTL, never the URL, signature or key) committed, else
  `unavailable` with `storage.operation` stage `audit`; unconfirmed outcomes record `object.upload_failed` (with the
  compensation result) and `object.deletion_pending`; denials record `access.denied`. Objects are at version 8.
- **Recovery and retention:** tombstone purge by the retention login only after provider absence and a ledger entry; pending
  and deleting rows are never selected by maintenance (pending age never proves an upload inert), reported by
  `recovery.sh status`, and repaired only through the guarded `DeleteObject` by an authorized actor
  ([RECOVERY.md](RECOVERY.md)). The binding metadata is captured and restored with the bytes.

## Organization logos

A logo upload uses the unchanged Put path (pending → ready, with its compensation) after core has validated and
re-encoded the image (PNG or JPEG, 16–2048 px per side, at most 512 KiB in and out; animated, SVG and other formats
refused), then associates the ready object as the Organization's current logo in one guarded transaction. An
association whose outcome is uncertain is re-read and reported truthfully (`publication_outcome_unknown`); the object is
retained and listed, never deleted while it may be published. Objects that are not the current logo are listed on the
management page and deleted only through the guarded `DeleteObject` path; reset and logo removal keep the objects. The
public logo route serves only the current ready logo of the Organization a trusted host resolves to.
