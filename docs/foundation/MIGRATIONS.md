# Database migrations

Migrations run in a one-shot container, never on the host and never inside the core server. The runner is `core/cmd/migrate` (package `core/internal/migrate`), built by `infra/docker/migrate.Dockerfile`. It is started through the Compose overlay `infra/compose/migrate.yml` together with `infra/compose/local.yml`.

## Tool

[goose](https://github.com/pressly/goose) `v3.28.0`, used as a Go library and pinned in `core/go.mod`. Migrations are goose SQL files in `core/migrations/`, named `NNNNN_name.sql`, each with `-- +goose Up` and `-- +goose Down` sections. They are embedded into the runner binary, so the image contains exactly the reviewed set.

Query generation is separate from migration execution. Core currently uses
handwritten pgx queries (the domain queries in `core/internal/domains/db/queries.go`
included); incremental sqlc adoption is a possible future, bounded trial.
It would generate typed query code, while Goose remains the migration runner.
No generator, parallel schema source or new CI requirement is introduced here.

## Roles and privileges

| Role | Used by migrations? |
|---|---|
| `<db>_migrator` | Logs in. Then runs `SET ROLE <db>_owner` on every connection. Has no privileges of its own in schema `app`. |
| `<db>_owner` (NOLOGIN) | Owns schemas `app` and `audit` (provisioning creates `audit` empty), every migrated object, and the migration metadata |
| `<db>_runtime` | Never. Core connects as this role. It cannot create objects, assume the owner or migrator roles, or read migration metadata. |
| `<db>_retention` | Never. The operator's retention login (version 9): it can delete only audit rows and deleted tombstones its own declared policy makes eligible ([RECOVERY.md](RECOVERY.md)). |

Role names derive from `DATABASE_NAME`. Before doing anything, the runner verifies that:

- the session user is `<db>_migrator`;
- the current role is `<db>_owner`;
- `<db>_owner` owns schema `app`;
- the session user is neither superuser nor BYPASSRLS.

Otherwise it refuses. Only the `migrate` service receives `DB_MIGRATOR_PASSWORD`; core, web and intelligence never do.

## Migration metadata

goose records history in `app.goose_db_version`. This is **system infrastructure, not a tenant-owned domain table**: it has no `organization_id` and no row-level security, and it is excluded from tenant-table policy checks by name.

- **Creation.** goose creates the table on the first use of *any* command (`status` and `version` included), in one transaction that also records version 0.
- **Protection.** The runner's store revokes every privilege on exactly that table and its identity sequence from PUBLIC, runtime, retention and migrator. It then verifies that both are owner-only, in the same transaction. If verification fails, nothing is committed.
- **Effect.** The schema's default sequence grant to the runtime role, which is meant for future application sequences, never reaches the metadata.

## Commands

Run from the repository root after `.env` exists. Each command prints tab-separated lines, ending with `current_version<TAB>N`. Exit codes:

- `0`: success.
- `1`: failure, including the identity preflight refusing to migrate (wrong role, or a superuser or BYPASSRLS session). Nothing is changed by a refusal.
- `2`: usage or configuration error, or `down`/`reapply` refused with `APP_ENV=production`. Nothing is changed.

Inspect (`status` lists each migration as `applied` or `pending`):

<!-- migrations:inspect -->
```sh
docker compose --env-file .env -f infra/compose/local.yml -f infra/compose/migrate.yml run --rm --build migrate status
docker compose --env-file .env -f infra/compose/local.yml -f infra/compose/migrate.yml run --rm --build migrate version
```

Apply all pending migrations:

<!-- migrations:apply -->
```sh
docker compose --env-file .env -f infra/compose/local.yml -f infra/compose/migrate.yml run --rm --build migrate up
```

Roll back the latest applied migration (one step):

<!-- migrations:rollback -->
```sh
docker compose --env-file .env -f infra/compose/local.yml -f infra/compose/migrate.yml run --rm --build migrate down
```

Roll back the latest applied migration and apply it again:

<!-- migrations:reapply -->
```sh
docker compose --env-file .env -f infra/compose/local.yml -f infra/compose/migrate.yml run --rm --build migrate reapply
```

`down` and `reapply` are refused with exit code 2 when `APP_ENV=production`. `run` starts PostgreSQL if it is not already running.

From version 21 a platform host is the Organization's generated, immutable platform label, resolved directly to its UUID; the friendly slug is metadata and its host routes nowhere ([DOMAINS.md](DOMAINS.md#platform-addresses-slugs-and-renames)). From version 18 a person signed in at the platform root can create a new Organization with themselves as its owner, only through the provision writer's definer body, and continue into its host through one-use continuation secrets; the signup credential is never a session ([IDENTITY.md](IDENTITY.md#platform-root-signup)). From version 17 Organization owners and admins read every Group's metadata but manage a Group only through an explicit Group owner/admin role or the owner-set, default-off Organization override, and never reach Group objects through an Organization role ([AUTHORIZATION.md](AUTHORIZATION.md)). From version 15 every Organization and Group keeps at least one owner (a database authority guard on role changes and binding deletions), runtime can delete role bindings only through the version-15 policies, and invitations are a forced table whose consumption only the claim writer's definer bodies write; the up refuses, with counts only, while any Organization or Group lacks an owner binding, and the down refuses while any invitation or invitation-era audit row exists ([TENANCY.md](TENANCY.md#membership-ownership-and-invitations)). From version 14 runtime can create Groups (the creator's `group_owner` binding is trigger-written), BusinessProfiles and associations, only through the onboarding INSERT policies, and still delete none of them ([TENANCY.md](TENANCY.md#group-onboarding)). From version 12 a browser session is bound to the origin and Organization it was issued for and resolves nowhere else ([IDENTITY.md](IDENTITY.md)). From version 11 a tenant host is a durable fact: an Organization slug or a verified custom-domain row decides which Organization a host routes to ([DOMAINS.md](DOMAINS.md)). From version 10 an MCP connection holds its own `mcp` session and stored Group selection, bound to one user and one Organization ([MCP.md](MCP.md)). From version 9 the retention login can delete only what its own declared policy makes eligible ([RECOVERY.md](RECOVERY.md)). From version 8 every committed change of the eight audited tables writes its audit event in the same transaction ([AUDIT.md](AUDIT.md)). From version 7 the stored-object metadata table is forced as well. From version 6 every tenant table, `users` and the three authentication tables have forced row-level security with per-command policies; see [DATABASE-ISOLATION.md](DATABASE-ISOLATION.md). Runtime can no longer create or delete tenant structure (Organizations, Groups, bindings, profiles, associations): those model primitives are trusted setup paths, and their public workflows belong to later stages (Group onboarding and membership administration).

## Adding a migration

1. Add `core/migrations/NNNNN_description.sql` with the next number and both sections. Objects go in schema `app`.
2. Grant the runtime role only what it needs, explicitly. Tenant tables need ENABLE and FORCE row-level security and per-command policies, following the pattern of `00006_row_level_security.sql` ([DATABASE-ISOLATION.md](DATABASE-ISOLATION.md)).
3. Verify in a disposable database: `up`, `down` and `up` again.

Test-only migrations never go in `core/migrations/`. The integration tests keep a synthetic probe in `core/internal/migrate/testdata/`.

## Reset implications

- `docker compose --env-file .env -f infra/compose/local.yml down -v` destroys the local database, including migration history. The next `up` recreates the roles from `.env` and starts again from version 0.
- `DATABASE_NAME` and the role passwords take effect only when the PostgreSQL volume is first created.

## Validation

`infra/validation/run.sh --base <commit> --allow-file <scope-allow-list> migrations` runs the integration tests against a disposable database: lifecycle, metadata privileges before and after the baseline, and runtime and migrator denials. It also runs the commands above verbatim, the identity catalog, the tenancy catalog, migration (empty, populated, repeated, restarted, down and up) and model tests, the BusinessProfile catalog, migration and model tests ([TENANCY.md](TENANCY.md)), the policy catalog, migration, guarded-access and ordering tests ([AUTHORIZATION.md](AUTHORIZATION.md)), the row-level security checks ([DATABASE-ISOLATION.md](DATABASE-ISOLATION.md)) and the stored-object catalog, migration, isolation, ordering and fault tests against a private MinIO ([OBJECT-STORAGE.md](OBJECT-STORAGE.md)). See [BOOTSTRAP.md](BOOTSTRAP.md).

**Test-database isolation.** After the verbatim commands (B-MIGRATE-CLI) and the catalog (B-MIGRATE-CATALOG) pass at the top version, the suite runs one read-only `migrate status` and copies the database once into a run-private, write-closed template `<DATABASE_NAME>_tpl` (`IS_TEMPLATE true`, `ALLOW_CONNECTIONS false`, CONNECT revoked). Before copying it checks that the database is pristine for the bound source: goose history equal to the bound migration files (version 0 plus every `NNNNN` file, read from the latest row per version; the raw history is recorded, never counted), the metadata and role facts, every row-bearing `app`/`audit` table empty, the database ACL, no database-qualified setting and no client session. Each independent integration invocation then starts on a fresh copy: `DROP DATABASE` (never `FORCE`; a client session is a refusal, never terminated), `CREATE DATABASE ... TEMPLATE`, and the exact CONNECT grants of `10-roles.sh`, under the canonical name, so role derivation, `current_database()` and the migrations are unchanged. The template record binds the migration digest, the provisioning scripts and the tested tree: a stale or mismatched template refuses. Lifecycle tests (`TestMigrationLifecycle`, the catalog and migration tests) still reset and step the schema themselves, starting from their own fresh copy; persist pairs get a fresh copy before the seed only. B-IT-ISOLATION proves the template and the refusals ([DATABASE-ISOLATION.md](DATABASE-ISOLATION.md#test-databases)); the run's `db-lifecycle.tsv` names every create, drop and refusal ([OPERATIONS.md](OPERATIONS.md#per-test-go-evidence)).
